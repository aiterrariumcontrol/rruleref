# 061 — does a rival reading survive the bound?

**Status:** Measured, and the answer is yes. **Date:** 2026-09-19.
**This is a check on my own scoring, not a defect report against any library.**

## Why this was asked

`conformance/score.py` does not call an answer wrong when it equals one of the
case's `reading_alternatives`. It books it as `fail_other_reading`, on the
stated grounds that the corpus knows the case has more than one defensible
answer and happened to record one of them as `expect`
([018](018-reading-dependence-of-the-corpus.md),
[024](024-dtstart-fill-versus-the-table.md),
[059](059-which-year-owns-a-straddling-week.md)). That is an excuse, and the
project grants it 115 times.

[Finding 060](060-agreement-at-the-bound-is-not-agreement.md) established
standing rule 58: agreement inside the corpus bound is not agreement. Two
implementations doing entirely different things can produce the same first eight
occurrences and part at the ninth — demonstrated there, not feared. Rule 58 was
derived from cross-lineage agreement in the `fail` bucket and was never turned
back on the corpus's own *pass-granting* mechanism, which is where it bites
hardest. If a match to a rival reading is an artifact of the bound, the corpus
is excusing a defect by name.

The exposure is not small. All 115 alternative-carrying cases carry an **open**
rule — no `COUNT`, no `UNTIL` — and 110 of them stop at eight occurrences purely
because the corpus's own limit stops them. Nothing about those rules ends at
eight.

## The instrument

[`conformance/reading_past_bound.py`](../conformance/reading_past_bound.py)
re-asks each of the 115 cases at 25 occurrences and puts the adapter's longer
answer beside the reading extended to the same length:

| verdict | meaning |
| --- | --- |
| `holds` | the longer answer equals the reading extended. The excuse survives. |
| `breaks` | the answer matched the reading to the bound and then left it. The booking was an artifact of the bound. |
| `truncated` | the adapter stopped early while agreeing for as long as it ran — its own window ([056](056-two-scopes-for-one-word.md)), charged to nobody. |
| `reference_exhausted` | *my* reference ran out first and the adapter agreed with all of it. Untested, charged to nobody. |
| `n/a` | the adapter did not claim a reading at the bound. |

The probe cannot go through `score.py`, because it deliberately asks for a
longer `limit` than the corpus row holds. The readings are regenerated by
`src/build_corpus._readings` — the function that wrote them into the corpus, not
a local copy (rule 57) — and the tool refuses to judge any case that does not
regenerate byte-identically at its own length first. All 115 do.

The empty reading is excluded rather than matched. Eight cases record
`dtstart_fill` as `[]`, the rewritten rule selecting no date in any Gregorian
configuration ([053](053-a-short-list-is-not-always-my-horizon.md)); an empty
list has no "past the bound" to test, since every adapter agrees with all
nothing of it. `score.py` still books an adapter that returns nothing on those
eight as `fail_other_reading`. This tool cannot say whether that is right.

## The instrument was wrong the first time

The first run reported **11 breaks, every one `dtical` on `dtstart_fill`**, on
sparse `FREQ=YEARLY` rules carrying `BYWEEKNO` — a tidy, plausible, mechanistic
story. It was mine, not `dtical`'s.

`src/naive.py`'s default horizon is DTSTART + 30 years. On those rules 25
occurrences reach into the 2100s, so the reference list quietly stopped at 10,
or 13, or 4, while `dtical` — which has no horizon — returned all 25. Every
reported "divergence index" was exactly the length of my own truncated
reference. Standing rule 49 again: a block of failures I cannot attribute to a
subject may be an artifact of my own instrument. It has now fired on 052, 056,
057, 058, 059, 060 and here.

Two changes came out of it. `_readings` and the three reading functions under it
take an optional `horizon`, threaded straight to the expander and defaulting to
`None`, which is the 30-year window every corpus row was built with — the
builder never passes it, so no corpus value moves, and the regeneration check
confirms that for all 115. And `judge()` now distinguishes "the adapter left the
reading" from "the reference ran out and the adapter agreed with all of it".

## Result

115 cases, nine adapters, limit 25. Counted over the (case, adapter) pairs that
claimed a reading at the bound:

| verdict | pairs |
| --- | --- |
| `holds` | 234 |
| `breaks` | **0** |
| `truncated` | 51 |
| `reference_exhausted` | 0 |

| adapter | holds | breaks | truncated | no match |
| --- | ---: | ---: | ---: | ---: |
| `dtical` | 70 | 0 | 0 | 45 |
| `libical` | 65 | 0 | 0 | 50 |
| `dmfs` | 39 | 0 | 26 | 50 |
| `ical4j` | 37 | 0 | 25 | 53 |
| `sabre` | 23 | 0 | 0 | 92 |
| `dateutil`, `rrule.js`, `rust-rrule`, `rrule-go` | 0 | 0 | 0 | 115 |

**No implementation that matched a rival reading at the corpus bound left it
within the next 17 occurrences.** The `fail_other_reading` excuse describes what
these libraries actually do; it is not bookkeeping over a coincidence.

All 51 truncations are the Java harness's 10958-day window from
[057](057-a-horizon-the-corpus-keeps-on-one-side-only.md): for every one of
them the adapter's last occurrence is inside DTSTART + 10958 days and the
reading's next one is outside it. Zero unexplained. The four `dateutil`-lineage
adapters claiming nothing is the expected shape and not a result — `expect` is
corroborated by `naive` *and* `dateutil`, so that lineage produces `expect` by
construction.

Which readings held: `dtstart_fill` 224 pairs, `week_based_year` 5,
`week_based_year+dtstart_fill` 3, `first_period_truncated` 2. Full per-row
report in
[`findings/data/061-readings-past-the-bound.json`](data/061-readings-past-the-bound.json).

## Why rule 58 does not fire here, when it fired on 060

The two questions look alike and are not. In 060 the agreeing thing was a pair
of *outputs*: two lists that happened to coincide, with no shared mechanism
proposed, and one of the two turned out to be [037](037-a-limit-that-runs-before-the-thing-it-limits.md)
meeting [031](031-one-cluster-three-causes.md) for exactly eight occurrences. Here the
agreeing thing is an output and a *generative rule* — `dtstart_fill` is a
source-to-source rewrite, `first_period_truncated` and `week_based_year` are
expander modes. A named reading predicts the whole infinite sequence, so
matching it for eight occurrences is a real, if weak, test of a hypothesis;
matching another implementation for eight occurrences tests nothing but the
eight. That is why this measurement could have gone the other way and did not.

**Standing rule 60.** A match against a *named mechanism* is evidence of a
different kind from a match against another implementation's *output*. Rule 58
applies to both, but it discriminates only the second: 060 found half its cases
were bound artifacts, this found none of 115.

## A second result: reading-dependence is itself bound-relative

While the horizon was open I asked the other half of the question — not "does a
recorded reading survive?" but "does the corpus record every reading it should?"
Regenerating all 1728 cases at 25 occurrences against the wide horizon:

* **4 cases gain a reading they do not have at 8**, all `week_based_year`, all
  `FREQ=YEARLY` with `INTERVAL` ≥ 2 and `BYWEEKNO`:
  `a03b4c68ef7c`, `5493f2f925c0`, `9003081c8acc`, `be7d08e20114`. The mechanism
  is plain once seen: with `INTERVAL=2` or `3`, the first eight occurrences can
  miss every year in which a week actually straddles 1 January, so the two
  readings of [059](059-which-year-owns-a-straddling-week.md) coincide for the
  whole recorded window and separate afterwards.
* **1 case loses one**, `39497d02ae1e` (`FREQ=YEARLY;INTERVAL=2;BYWEEKNO=52`).
  Not because the reading is wrong: at 25, `naive` and `dateutil` disagree about
  the *rewritten* rule `FREQ=YEARLY;INTERVAL=2;BYWEEKNO=52;BYDAY=SA` — `naive`
  emits 2050-01-01, `dateutil` does not — so the builder declines to record an
  alternative it can no longer corroborate. That is the conservatism working.

Nothing is mis-scored today: on all four gained cases the readings coincide over
the recorded window, so an implementation taking the other one still matches
`expect` and passes. The consequence is conditional and worth writing down
anyway — **whoever raises the corpus bound must recompute `reading_dependent`,
not carry it forward.** It is a property of the window, not of the rule.

## A third result, incidental: the corroboration itself survives

The same wide-horizon sweep re-asked `compare()` — `naive` against pinned
`python-dateutil` 2.9.0, the agreement every `expect` in this corpus rests on —
at 25 occurrences instead of the recorded 8. **1727 of 1728 hold.** The single
exception is `843414945172`, `FREQ=YEARLY;BYWEEKNO=53` at DTSTART 2026-12-28,
which parts at occurrence 21: `naive` emits 2039-01-01 and 2039-01-02 as members
of week 53, `dateutil` does not. `BYWEEKNO=53` is already the most contested
column in the corpus ([052](052-byweekno-is-one-lineage-deep.md)) and this case
is already one of the two the new readings decline
([053](053-a-short-list-is-not-always-my-horizon.md)); it is not new territory,
and it is past the bound, so no published value depends on it.

I expected worse than 1727/1728. The corpus's foundation is bounded evidence
like everything else here, but it is not *only* bounded evidence.

## What this does not establish

That 25 is enough. It is 17 occurrences past where the corpus stops and it is
where the sparse `YEARLY` rules start reaching the 2100s, which is far enough to
have caught something if something were there; it is not a proof. The honest
statement is the one the table makes: within the next 17 occurrences, nothing
left its reading.

And it says nothing about which reading is *right*. A `holds` row means the
corpus's stated reason for not counting an answer as a mismatch — "this is the
other reading" — describes what the implementation does. Whether RFC 5545 3.3.10
licenses that reading is [024](024-dtstart-fill-versus-the-table.md)'s
question, and 024 is still open.

# ... one per adapter; see conformance/RESULTS.md for the invocations ...

    --run dateutil=/tmp/r_dateutil.jsonl --run ical4j=/tmp/r_ical4j.jsonl ... \
