# 007 — RFC 5545 §3.6.5's own `VTIMEZONE` examples: three verified, two defective

*Status: reported here, not filed anywhere. Verified 2026-09-06 against a
sha256-pinned copy of RFC 5545 and the IANA time zone database.*

Everything this project had checked about time zones so far took the zone as
given — `DTSTART;TZID=America/New_York`, and the tz database answers what the
offset was. A `VTIMEZONE` component is the other case: a calendar that
**carries its own transition rules** instead of naming a zone. It is the one
place in RFC 5545 where recurrence expansion is not scheduling but the
*definition of what a wall-clock time means*, so an error in a `VTIMEZONE`
`RRULE` moves every floating time in the calendar silently.

§3.6.5 prints five example components. All five are extracted by program from
the pinned text (`src/vtimezone.py`), resolved into an offset function, and run
(`tests/test_vtimezone.py`, 30 assertions, all passing).

## What holds up

**The New York examples are exactly right.** Example 1 claims to show "all the
time zone rules for New York City since April 30, 1967 at 03:00:00 EDT". It
does. Expanding its seven observances produces **145 transitions between
1967-04-30T07:00Z and 2040**, and that set is *identical* to the transitions
bisected out of the IANA database for `America/New_York` — same instants to the
second, same offsets, and `TZNAME` agrees at all 91,007 sampled instants.
Example 3, the "current rules" form, likewise matches on all 65 transitions
from 2007. The awkward middle of US history is in there and correct: the
one-off 1974-01-06 and 1975-02-23 starts, carried by `DTSTART`+`RDATE` with no
`RRULE` at all.

This matters because the expected values come from a source that is not RFC
5545 and was not written by its authors. It is the strongest evidence class
this repository has produced for the timezone half of the spec.

**Example 2's stated bounds are exact.** The RFC says the two-onset form is
"only suitable for a recurring event that starts on or later than March 11,
2007 at 03:00:00 EDT ... and ends no later than March 9, 2008 at 01:59:59 EST".
Checked to the second: the component agrees with tzdata across the whole
window, `2008-03-09 01:59:59 EST` is the last instant at which it does, and one
second later it is wrong. A tighter self-description than specifications
usually manage.

`dateutil.tz.tzical` — a separately written iCalendar reader — agrees with this
project's resolver on all five examples over every instant sampled.

## Defect 1 — `UNTIL` violates a MUST in the same section

§3.6.5:

> If observance is known to have an effective end date, the "UNTIL" recurrence
> rule parameter MUST be used to specify the last valid onset of this
> observance (i.e., the UNTIL DATE-TIME will be equal to the last instance
> generated by the recurrence pattern). It MUST be specified in UTC time.

Examples 4 and 5 both contain:

```
DTSTART:19870405T020000
RRULE:FREQ=YEARLY;BYDAY=1SU;BYMONTH=4;UNTIL=19980404T070000Z
TZOFFSETFROM:-0500
```

The rule generates first Sundays of April at 02:00 local, which with
`TZOFFSETFROM:-0500` are `…T070000Z`. **1998-04-04 is a Saturday.** The first
Sunday of April 1998 is the 5th. So `UNTIL` equals no instance the pattern
generates: the last instance at or before it is `19970406T070000Z` and the next
is `19980405T070000Z`.

Example 1's four `UNTIL` values all satisfy the requirement exactly, which is
why this reads as a slip rather than a different reading of the rule.

**Observable consequence, in the RFC's own words.** Example 5's prose says
"There is a second Daylight Time rule that picks up where the other left off."
It does not. With the printed value the first rule's last onset is 1997-04-06
and the second rule begins in 1999, so **the whole of 1998 is standard time** —
1 July 1997 is `-04:00`, 1 July 1998 is `-05:00`, 1 July 1999 is `-04:00`
again. A year silently disappears from the observance the example exists to
illustrate.

That gap is also the argument about intent. Two corrections are possible —
`19970406T070000Z` (end after 1997) or `19980405T070000Z` (end after 1998) —
and only the second makes the prose true and leaves no hole. That is an
inference, not something the RFC states.

## Defect 2 — an example inside the region §3.8.5.3 declares undefined

Example 5's second `DAYLIGHT` observance:

```
DTSTART:19990424T020000
RRULE:FREQ=YEARLY;BYDAY=-1SU;BYMONTH=4
```

**1999-04-24 is a Saturday**; the last Sunday of April 1999 is the 25th. The
`DTSTART` does not satisfy its own rule.

§3.6.5 says "The onset DATE-TIME values for the observance defined by the time
zone sub-component is defined by the 'DTSTART', 'RRULE', and 'RDATE'
properties", so `DTSTART` is itself an onset — example 1's 1974 observance has
no `RRULE` and depends entirely on that reading. The component therefore
declares **two daylight onsets one day apart**, `1999-04-24T07:00Z` and
`1999-04-25T07:00Z`. And §3.8.5.3 says the recurrence set is undefined when
`DTSTART` is not synchronized with the rule, so a reader is entitled to almost
anything here. `dateutil.tz.tzical` takes the same reading as this project and
emits both.

This is the same class of problem finding 004 corrected in this repository's own
corpus, appearing in the specification's illustrative material.

## Provenance and prior art

Both defects are inherited verbatim from **RFC 2445** (November 1998),
§4.6.5 — same `UNTIL=19980404T070000Z`, same `DTSTART:19990424T020000`
(`sha256 21bfccbb…aa828` of `rfc-editor.org/rfc/rfc2445.txt`). They have been
in the iCalendar specification for roughly twenty-eight years and across one
revision.

The [RFC 5545 errata list](https://www.rfc-editor.org/errata/rfc5545) was read
in full on 2026-09-06: 39 entries, of which two touch §3.6.5 (5215 and 8398,
both about the `tzprop` ABNF) and one (3740, Verified) replaces the
`VTIMEZONE` in §4 for an unrelated coverage reason. **None reports either
defect above.** A web search for the literal `UNTIL` value found no report
either. That is a search, not a proof of absence.

## How much this matters

Not much operationally, and the honest version should be said plainly: the
affected component is explicitly labelled *fictitious*, no real calendar
depends on it, and a real implementation that copies it copies a zone that
does not exist. What it costs is the thing examples are for. Someone learning
`VTIMEZONE` from §3.6.5 sees a `MUST` stated in prose and then contradicted two
pages later by the illustration of that same `MUST`, and sees a rule/`DTSTART`
pair whose recurrence set the specification elsewhere refuses to define. The
one place in the document that shows what an "effective end date" looks like
shows it wrong.

## Reproducing

```
PYTHONPATH=<dateutil> python3 tests/test_vtimezone.py
```

Requires a copy of RFC 5545 at `$RFC5545_TXT` matching the pinned sha256, and
the system tz database. `src/vtimezone.py` run directly prints the five
extracted components.
