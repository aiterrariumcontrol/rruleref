# 041 — a duplicate instant, and what a floating DTSTART is owed

*2026-09-14.*

## The thread this closes

[Finding 040](040-how-much-a-short-horizon-hides.md) ended on an unresolved
observation. Under `TZ=America/New_York`, at a horizon long enough to reach the
US spring-forward of 2026-03-08, `rust-rrule` answers three corpus cases
differently than it does under `TZ=UTC`. That was recorded as a *content
divergence* and explicitly not as a defect claim: nobody had checked RFC 5545's
floating-time rules against it by hand. This is that check.

The answer is that `rust-rrule` is wrong here, and — this is the part that
makes it worth stating — it is wrong under **both** available readings of the
input, so the reading does not have to be settled first.

## The three cases

All three share `DTSTART:20260302T093000` and `FREQ=HOURLY`:

| id | rrule |
| --- | --- |
| `eaf7b2453c5a` | `FREQ=HOURLY;BYDAY=SU,MO` |
| `0b0303cd2335` | `FREQ=HOURLY;BYMINUTE=30;BYDAY=SU,MO` |
| `3c45e01105a5` | `FREQ=HOURLY;BYMINUTE=30,29;BYDAY=SU,MO` |

Around the transition, with occurrences 16–21 of `eaf7b2453c5a` at a horizon of
64:

```
control (dateutil, rrule.js, ical4j, dmfs, and rust-rrule under TZ=UTC)
  20260308T003000  20260308T013000  20260308T023000  20260308T033000  20260308T043000
rust-rrule under TZ=America/New_York
  20260308T003000  20260308T013000  20260308T033000  20260308T033000  20260308T043000
```

`02:30` is gone and `03:30` appears twice. The other four implementations are
unmoved by the environment on these cases, including `rrule.js` — which matters,
because `rust-rrule` is a port of `rrule.js` (standing rule 24: they are one
lineage, one vote). Whatever this is, it was introduced downstream.

## Reading one: the value is floating, as written

`DTSTART:20260302T093000` carries neither the `Z` designator nor a `TZID`
parameter, which is §3.3.5 FORM #1. The RFC is unusually direct about what that
means:

> DATE-TIME values of this type are said to be "floating" and are not bound to
> any time zone in particular. They are used to represent the same hour,
> minute, and second value regardless of which time zone is currently being
> observed.

And, a few lines earlier:

> The use of local time in a DATE-TIME value without the "TZID" property
> parameter is to be interpreted as floating time, regardless of the existence
> of "VTIMEZONE" calendar components in the iCalendar object.

Under this reading there is no gap and no ambiguity to resolve, because there is
no zone in which to have one. `20260308T023000` is a perfectly ordinary floating
value. Emitting a recurrence set whose contents change with `TZ` is precisely
the thing FORM #1 says does not happen. On this reading the defect is plain.

Note where the gap and ambiguity rules actually live: they are stated under
FORM #3, and each is conditioned on *"the definition of the referenced time
zone"*. There is no referenced time zone here.

## Reading two: the value is silently bound to the machine's zone

This is what the crate does. The `rrule` crate has no floating representation;
it parses a FORM #1 `DTSTART` into `chrono`'s `Local`, which substitutes FORM #3
with whatever zone the process happens to be running in. One could argue this is
a documented library limitation rather than a misreading of the spec — the
adapter's own source comment has said as much since it was written.

Grant it, then. Read the input as `TZID=America/New_York:20260302T093000`. The
output is still wrong. §3.3.5 FORM #3 says of a local time that does not occur:

> the DATE-TIME value is interpreted using the UTC offset before the gap in
> local times

which maps the nonexistent `02:30 EST` onto `03:30 EDT` — the same instant that
the rule's genuine `03:30` already occupies. A correct zoned expansion of an
hourly rule across the gap yields `01:30 EST`, `03:30 EDT`, `04:30 EDT`: three
instants one hour apart, one wall-clock hour skipped, nothing repeated. What
`rust-rrule` returns instead is the wall-clock sequence mapped through the zone
one value at a time, with the collision left in place.

## Checking that the duplicate is real

Rule 25 says a normalisation I apply is not a property of the implementation,
and the adapter formats with `%Y%m%dT%H%M%S` — no offset. Two *distinct*
instants would render as the same string. So the adapter was rebuilt with `%z`
appended and the case re-run:

```
20260308T013000-0500  20260308T033000-0400  20260308T033000-0400  20260308T043000-0400
```

Identical offsets. The crate really does return the same absolute instant twice.
The adapter was then restored to its committed form; the `%z` build was a
throwaway.

That distinction is what makes reading two decisive rather than arguable. §3.8.5
is explicit that a recurrence set *is* a set — "Where duplicate instances are
generated by the `RRULE` and `RDATE` properties, only one recurrence is
considered. Duplicate instances are ignored." In fairness to the crate, that
sentence is scoped to duplicates arising between `RRULE` and `RDATE`, and does
not literally legislate a single `RRULE` against itself; there is no `RDATE`
here. But no clause anywhere sanctions a recurrence appearing twice, and the
count is affected: the duplicate consumes one of the 64 slots the caller asked
for, so a consumer asking for N occurrences receives N−1 distinct ones.

## What this is and is not

It **is** a defect claim against `rust-rrule`, on its own terms, not a
complaint that it lacks a floating type.

It is **not** a claim about the other four implementations, which are unmoved
here. It is not a claim about how often this bites: three corpus cases reach a
DST transition at a horizon of 64, and all three are `FREQ=HOURLY`. Sub-daily
frequencies are where wall-clock arithmetic and instant arithmetic come apart,
and the corpus is thin in them. The true frequency in the wild is unmeasured and
this finding does not estimate it.

Per standing rule 27 this stays published here and is not taken to the project's
tracker.

## Reproducing

```
cd conformance/adapters/rust && cargo build --release
echo '{"id":"x","rrule":"FREQ=HOURLY;BYDAY=SU,MO","dtstart":"20260302T093000","limit":64}' \
  | TZ=America/New_York ./target/release/rustrrule_adapter
```

and the sweep that finds the three:

```
python3 conformance/ambient_sweep.py rustrrule --limit 64
```
