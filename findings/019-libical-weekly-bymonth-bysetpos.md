# 019 — libical loses occurrences in the week that straddles a BYMONTH boundary

**Status:** Open. Reproduced against libical master, unreported, and
**unauthorized to report** — sending it upstream is a HUMAN_ACTION request that
has not been made.

**Date:** 2026-09-07.
**Affects:** libical master `48d52b4`, built from source; also present in
Debian trixie's 3.0.20 inside a much larger `BYSETPOS` failure class.
**Supersedes:** the closing section of
[finding 017](017-libical-third-lineage.md), via
[finding 018](018-reading-dependence-of-the-corpus.md).

## The claim

For `FREQ=WEEKLY` with `BYMONTH` and `BYSETPOS`, libical loses occurrences that
fall inside a selected month but in a week that begins in a month `BYMONTH`
does not select. Eight of libical master's 87 corpus failures are this; they
are every `FREQ=WEEKLY` failure it has.

RFC 5545 §3.3.10 fixes the order. `BYSETPOS`

> MUST only be used in conjunction with another BYxxx rule part [...] it
> specifies [...] the nth occurrence of the specific occurrence within the set
> of recurrence instances generated by the rule.

and the rule parts are evaluated `BYMONTH` first, `BYSETPOS` last. The set
`BYSETPOS` indexes is therefore the set *after* `BYMONTH` has limited it.

## Two paths, both observed

**(a) `BYSETPOS` indexes the un-limited set in the straddling week.**

```
DTSTART:20260705T090000                     (Sunday)
RRULE:FREQ=WEEKLY;BYDAY=MO,SU,TU;BYMONTH=7;BYSETPOS=1
  corpus  : 20260705, 20260706, 20260713, ...
  libical : 20260706, 20260713, 20260720, ...
```

The week is Mon 2026-06-29 .. Sun 07-05. `BYDAY` gives Mon 06-29, Tue 06-30,
Sun 07-05; `BYMONTH=7` limits that to `{07-05}`; position 1 is 07-05. libical
takes position 1 of the un-limited three and gets 06-29, which `BYMONTH` then
rejects, so the week yields nothing.

The same rule with `BYSETPOS=2` shows the shift rather than the loss:

```
RRULE:FREQ=WEEKLY;BYMONTH=7;BYDAY=SU,TU;BYSETPOS=2   DTSTART:20260705T090000
  corpus  : 20260712, 20260719, ...
  libical : 20260705, 20260712, ...
```

Position 2 of `{Tue 06-30, Sun 07-05}` is 07-05, which survives `BYMONTH`; the
limited set `{07-05}` has no position 2 and the week correctly yields nothing.

Two controls: with a single `BYDAY` value the un-limited and limited sets
coincide and libical agrees (`FREQ=WEEKLY;BYDAY=SU;BYMONTH=7;BYSETPOS=1` from
the same DTSTART returns 20260705). Without `BYSETPOS` libical also agrees.
So this is `BYSETPOS`-specific and not a `BYMONTH` filtering bug.

**(b) The straddling week is skipped outright when arriving from a gap.**

```
RRULE:FREQ=WEEKLY;BYMONTH=8;BYDAY=SU,TU;BYSETPOS=-1
  DTSTART:20270727T090000  -> 20270801, 20270808, ...   (correct)
  DTSTART:20260802T090000  -> ..., 20260830, 20270808   (20270801 lost)
```

Same rule, same week Mon 2027-07-26 .. Sun 08-01, two different answers
depending on whether iteration entered that week from DTSTART or arrived at it
after eleven non-selected months. Path (a) does not explain this one:
`BYSETPOS=-1` of the un-limited `{Tue 07-27, Sun 08-01}` is 08-01, which
`BYMONTH` accepts. `FREQ=WEEKLY;BYMONTH=7,8;BYDAY=SU,TU;BYSETPOS=-1` from
20260802 skips Sun 2027-07-04 the same way and resumes at 07-11.

I have not read the libical source for either path and make no claim about
where in `icalrecur.c` they live. Both are stated as observed behaviour.

## Prior art

libical [#795](https://github.com/libical/libical/issues/795) — "`BYSETPOS` not
fully supported" — is **closed**, and its `FREQ=WEEKLY;BYDAY=MO,TU,WE,TH,FR;
BYSETPOS=1,3` example now returns the expected instances on master. #21 and #67
are the older `BYSETPOS`-ignored reports, also closed.
[#1276](https://github.com/libical/libical/issues/1276) is `FREQ=YEARLY`
expand-vs-limit and unrelated. A search of the tracker for `BYSETPOS` returns
nothing open. Finding 017's conclusion — that every 3.0.20 failure falls inside
libical's own documented known-issue set — **does not hold for master**: these
eight are outside it.

## Reproducing

Build master as described in
[`conformance/adapters/c/README.md`](../conformance/adapters/c/README.md), then

```sh
LD_LIBRARY_PATH=$PWD/libical-install/lib \
  python3 conformance/score.py --json /tmp/master.json -- \
  conformance/adapters/c/libical_adapter
```

Scores at the time of writing: master `48d52b4` 1599 pass / 87 fail / 35 error;
Debian 3.0.20 1510 / 154 / 57. Saved as
[`data/019-libical-master-score.json`](data/019-libical-master-score.json) and
[`data/019-libical-3.0.20-score.json`](data/019-libical-3.0.20-score.json).

## What would have to be true for this to be my defect instead

The corpus's expected values here are corroborated by `naive` and `dateutil`,
and finding 018 confirms these eight are *not* reading-dependent: the two
readings of the first period agree on all of them, so they do not rest on
finding 004's contested choice. What they do rest on is the ordering of
`BYMONTH` before `BYSETPOS`, which §3.3.10 states directly. If that reading of
the ordering is wrong, all eight are mine and finding 018's retraction of 017
still stands on its own.
