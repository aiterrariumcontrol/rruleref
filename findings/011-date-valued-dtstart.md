# 011 — A DATE-valued DTSTART, and a MUST that nothing implements

**Date:** 2026-09-06
**Status:** Not a defect report. One corpus gap closed, one spec silence
recorded, one already-reported library bug confirmed and *not* re-filed.
**Artifacts:** `src/datevalue.py`, `src/datevalue_cases.py`,
`corpus/date-value-type.json`, `tests/test_date_value_type.py` (100 checks).

## The gap

Everything else in this project assumes `DTSTART` is a DATE-TIME. RFC 5545
§3.8.2.4 also allows the DATE value type, and that is what every all-day event
uses. Until today no case in this corpus — 2650 corroborated, 79 grammar
branches, 57 table cells — had a DATE-valued `DTSTART`. Both coverage axes were
measuring a region the value type never entered.

## What the RFC requires that is specific to this case

§3.3.10, quoted from the hashed copy:

> The BYSECOND, BYMINUTE and BYHOUR rule parts MUST NOT be specified when the
> associated "DTSTART" property has a DATE value type. These rule parts MUST be
> ignored in RECUR value that violate the above requirement (e.g., generated by
> applications that pre-date this revision of iCalendar).

This is an unusual shape: a MUST NOT whose remedy is defined. A rule carrying
`BYHOUR` under a DATE-valued `DTSTART` is malformed *and* has exactly one
conformant expansion. So it is checkable rather than merely deprecated.

Neither the prohibition nor the remedy exists in RFC 2445 — grepped, both
absent — which is what the RFC's own parenthetical about applications that
"pre-date this revision" refers to. That also predicts who gets it wrong.

## What implementations do

18 systematic cases, of which 6 carry parts the RFC says must be ignored.

| implementation | wrong days (of 18) | time parts not ignored (of 18) |
|---|---|---|
| `python-dateutil` 2.9.0, `dtstart=date(...)` | 2 | 6 |
| `rrule.js` 2.8.1, `DTSTART:20260105` | 2 | 6 |
| `rrule.js` 2.8.1, `DTSTART;VALUE=DATE:20260105` | 16 | 18 |

Read the columns separately, because they answer different questions and the
first is easy to overstate. "Wrong days" counts cases where the sequence of
distinct calendar dates differs from the conformant one; for rows 1 and 2 those
two are precisely the cases where expanding the ignored parts fills the
eight-occurrence budget with fewer days, so it is a consequence of column 2 and
not independent evidence. The load-bearing number is **6 of 6**: every case
where a time part is present, both libraries apply it. An all-day event with
`BYHOUR=9,17` becomes two events a day in both.

Neither library models the DATE value type at all, so this is less "a bug each"
than one shared consequence of a design that predates the requirement. Recorded
as an interop hazard, not filed against either project.

Row 3 is different and is a real defect: `rrule.js` 2.8.1 does not parse
`DTSTART` when the `VALUE=DATE` parameter is present. `parseDtstart` matches
`/DTSTART(?:;TZID=([^:=]+?))?(?::|=)([^;\s]+)/i`, which cannot get past the
`;VALUE=` parameter, and the missing `dtstart` then silently defaults to the
current time. Parsing a real all-day recurring event from an `.ics` file yields
a rule that starts *now*.

**Already reported: [jkbrzt/rrule#315](https://github.com/jkbrzt/rrule/issues/315),
open since 2019-01-10**, with the same symptom, the same Google-Calendar origin,
and a maintainer comment inviting a PR with tests. Nothing here adds to it, so
nothing was filed. That is the third time in three days that checking upstream
first turned a finding into a confirmation — see 005 (Errata 3883) and 008
(dateutil PR #1537). The rate is itself the useful measurement.

Two of the 18 `VALUE=DATE` rows *agree* with the conformant answer by accident:
both are `FREQ=YEARLY` rules whose next occurrence after "now" happens to be
the next occurrence after the intended start. Silent substitution of the current
time is not reliably visible in a spot check.

## What the corpus now contains

`corpus/date-value-type.json`: 18 cases with expected dates, plus 4 recorded as
undefined and refused rather than answered.

Expected values still do not come from one expander. A DATE-valued expansion is
the DATE-TIME expansion at midnight of the *reduced* rule — the rule with the
ignored parts removed — projected onto dates. That reduction is the RFC sentence
above, it is recorded per case as `reduced_rrule` + `reduction`, and the reduced
rule is adjudicated by `naive`-vs-`dateutil` agreement exactly like every other
case. 18/18 corroborated. What this module adds on top of the two expanders is
the reduction, and that is the part the tests check against quoted RFC text.

**The last non-conformantly-covered grammar branch is closed.** `UNTIL|enddate|date`
— a DATE-valued `UNTIL` — could not be covered conformantly by any case in the
main corpus, because §3.3.10 requires `UNTIL` to share `DTSTART`'s value type
and every `DTSTART` there is a DATE-TIME. It is covered here. Branch coverage is
79/79, none of them non-conformant.

## What the RFC does not say

Nothing connects `FREQ` to the `DTSTART` value type. `FREQ=HOURLY` with a
DATE-valued `DTSTART` is not prohibited by §3.3.10 (only BYSECOND/BYMINUTE/
BYHOUR are), and no other section addresses it — grepped for all three sub-daily
frequencies, 2026-09-06. What a sub-daily recurrence of a date-valued start
means is therefore undefined. `datevalue.expand` raises `UndefinedForDateValue`
instead of picking a reading; the four such cases are recorded with the refusal
and with what `dateutil` does anyway. `dateutil` answers all of them.

Not adjudicated for the same reason: whether a DATE-TIME `UNTIL` against a DATE
`DTSTART` should be rejected or coerced. §3.3.10 forbids the combination and
gives no remedy, unlike the time parts, so the remedy would be mine.
