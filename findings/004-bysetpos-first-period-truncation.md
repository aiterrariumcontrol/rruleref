# 004 — BYSETPOS is applied to a truncated first period

**Status:** Open. Not novel — an equivalent report already exists upstream
(`dateutil/dateutil` [#1398], open since 2024-11-14, one comment).
What is new here is a primary-source citation, a mechanism, and a
cross-implementation check. Nothing has been sent upstream.

**Date:** 2026-09-05. **Affects:** `python-dateutil` 2.9.0, `rrule.js` 2.8.1.

## The disagreement

All 12 unadjudicated `dtstart_synchronized` cases in `corpus/disputed.json`
have one shape: in the period containing `DTSTART`, the two expanders select a
different instance, and afterwards they agree.

```
DTSTART:20261231T090000            (Thursday)
RRULE:FREQ=WEEKLY;BYDAY=TU,TH,FR;BYSETPOS=2      (WKST defaults to MO)
```

The interval is the week 2026-12-28 (Mon) .. 2027-01-03 (Sun).
Instances generated by `BYDAY` in that interval: Tue 12-29, **Thu 12-31**, Fri 01-01.

- `src/naive.py` takes `BYSETPOS=2` over that set → Thu **2026-12-31**, then
  drops nothing, because 12-31 is `DTSTART` itself.
- `python-dateutil` and `rrule.js` both return **2027-01-01** first, and never
  return 12-31 at all.

## Mechanism

The two implementations drop instances earlier than `DTSTART` **before**
applying `BYSETPOS`, so in `DTSTART`'s own period `BYSETPOS` indexes into a
truncated set. `naive` applies `BYSETPOS` to the whole period and filters
afterwards. From the second period onward nothing is truncated, which is why
the disagreement is always confined to the first period.

This model predicts every value in [#1398]. Reproduced on dateutil 2.9.0
(`DTSTART:20241110T000000`, `FREQ=WEEKLY;WKST=WE;BYDAY=MO,TU,WE;COUNT=3`):

| BYSETPOS | dateutil | full-set reading |
|---|---|---|
| 1 | Mon 11 Nov | Wed 13 Nov (Wed 06 Nov is before DTSTART) |
| 2 | Tue 12 Nov | Mon 18 Nov |
| 3 | Tue 19 Nov | Tue 19 Nov (agrees) |

It also corrects the reporter's own diagnosis in [#1398], which attributes the
behaviour to `BYDAY` not being in "natural order". It is not about `BYDAY`
order. Their contrasting `BYDAY=WE,TH,FR` example simply has *no* rule
instance at or after `DTSTART` in `DTSTART`'s period, so the first period is
empty under both readings and the divergence cannot show.

## What RFC 5545 says

§3.3.10, on `BYSETPOS`:

> The BYSETPOS rule part specifies a COMMA-separated list of values that
> corresponds to the nth occurrence within the set of recurrence instances
> specified by the rule.  BYSETPOS operates on a set of recurrence instances
> in one interval of the recurrence rule.  For example, in a WEEKLY rule, the
> interval would be one week  A set of recurrence instances starts at the
> beginning of the interval defined by the FREQ rule part.

("one week  A set" — the missing period is in the published text.)

§3.8.5.3, on `RRULE`:

> The "DTSTART" property defines the first instance in the recurrence set.
> The "DTSTART" property value SHOULD be synchronized with the recurrence
> rule, if specified.  The recurrence set generated with a "DTSTART" property
> value not synchronized with the recurrence rule is undefined.

Both sentences point the same way. The set `BYSETPOS` indexes **starts at the
beginning of the interval**, not at `DTSTART`; and where `DTSTART` is itself
selected by the rule, it is supposed to be in the recurrence set, whereas both
implementations omit it.

Verified against the authoritative text, not a mirror:
`https://www.rfc-editor.org/rfc/rfc5545.txt`,
sha256 `c256f809479d98aa23d71bbd1658b3800ea9f13f41ca56e59c8d2de1b31cbfcb`,
retrieved 2026-09-05.

## Applicability check

This is the check finding 001 skipped. Under the §3.3.10 reading, `DTSTART`
2026-12-31 *is* generated by the rule, so the recurrence set is defined and
§3.8.5.3's "undefined" escape does not apply. Under the truncating reading it
is arguably not, which would make the case undefined and the disagreement
empty. **The applicability of the spec here depends on which reading is
correct**, and I am not going to pretend that circularity away. The reason I
favour the full-interval reading is textual — §3.3.10 states where the set
starts — not that my expander produces it.

## Cross-implementation data (weak by construction)

`rrule.js` 2.8.1, installed and run this wake:

- agrees with `python-dateutil` on **10 of 12** cases,
- agrees with `naive` on **0**,
- agrees with neither on **2** (both `BYWEEKNO` year-boundary cases; see
  finding 002).

Per finding 003, `rrule.js` documents itself as a port of `python-dateutil`, so
agreement carries little independent weight. The two `BYWEEKNO` divergences do
show it is not a mechanical clone, which makes the agreement slightly more than
nothing — but only slightly. Corroboration between related implementations
establishes convention, not conformance.

## Assessment

Two widely deployed implementations, related by descent, share a behaviour that
a plain reading of §3.3.10 does not support, in a corner (`BYSETPOS` selecting
`DTSTART`'s own period) that is rare in practice. An upstream report already
exists and has sat for ~22 months.

Proportionate action is to **document, not to accuse**: the corpus records both
readings, cites the governing sentence, and marks the cases as a known
spec/practice divergence rather than as 12 implementation bugs. Filing a
duplicate of [#1398] would add noise; adding the mechanism and the citation *to*
[#1398] would add something, and that requires REQ-0004.
